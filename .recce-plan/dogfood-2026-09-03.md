## Friction

### 1. Serve default-port mismatch: docs say 8443, CLI says 8008 · size XS
`python3 -m recce serve --help` shows `--port PORT (default 8008)`.
The QUICKSTART.md + docs/reference/webui.md I just wrote in the
0.7.1 docs sync use 8443 throughout (because that's the port every
live-testing session in the P7 audit used — a stale operator habit
that leaked into the docs). `doctor`'s next-step text also says 8008.

**Fix:** either
  (a) update QUICKSTART + webui.md + all doc examples to say 8008
      (matches CLI default), OR
  (b) change the CLI default to 8443 (breaks anyone who bookmarked
      8008; changes the doctor next-step too).

Recommendation: (a) — docs alignment. 8008 is the shipped default
and the tests use it. ~10 lines across 2-3 files.

### 2. `udp-basic: skipped` noise: 21 lines per phase · size XS
Every host prints:
```
[~] 172.20.0.14: udp-basic: skipped (needs root/CAP_NET_RAW for raw
    UDP); run with sudo, or use --udp-top in the vulns phase
```
That's 21 duplicated warnings for a 21-host run. It's the same
condition (running unprivileged), not per-host state — should print
ONCE at scan start ("running unprivileged; UDP checks skipped") and
then just `[i/N] <ip>: k port(s)` per host.

**Fix:** in the enum phase, hoist the udp-basic skip check to the
scan preamble; suppress the per-host warning when it's already been
announced. `recce/cli/_phases.py` or wherever `udp-basic: skipped`
originates.

### 3. `21 scan issue(s) logged (0 error, 21 incomplete)` spurious warning · size S
Every reports-written footer prints
`[!] 21 scan issue(s) logged (0 error, 21 incomplete)` because the
`udp-basic: skipped` entries land as "incomplete" scan issues. On
an unprivileged run those aren't really incomplete — they're
expected. The workbook's Overview tab shows the 21 incomplete
count too, misleading a tester into thinking scan phases failed.

**Fix:** either
  (a) don't emit a scan issue when the reason is
      "unprivileged (needs CAP_NET_RAW)" — it's a config state, not
      a scan failure, OR
  (b) categorise issues into `skipped_by_config` vs `incomplete`
      and only alert on the second in the summary footer.

Recommendation: (a). Scan-issue rows should model actual failures,
not conditional-execution skips.

### 4. API response-key inconsistency across endpoints · size S
Different endpoints use different top-level keys for their list
payload:

| Endpoint | Key |
|---|---|
| `/api/hosts` | `items` |
| `/api/findings` | `items` |
| `/api/credentials` | `items` |
| `/api/scan/suggestions` | `suggestions` |
| `/api/scan/context` | `commands` |
| `/api/act` | `top`, `tiers` (no unified list) |
| `/api/attack-chain/{ad,cloud,web}` | `steps`, `edges` |

Users of the API (fieldkit, third-party scripts, CLI wrappers) have
to remember which key to read per endpoint. The `items` convention
should be the default; the specialised endpoints can also keep their
domain-specific keys as aliases if renaming would break consumers.

**Fix:** add `items` as a synonym for `suggestions` in
`/api/scan/suggestions` (both point at the same list). Same for
`commands` in scan/context if useful. Or, less invasively, document
the actual key per endpoint in `docs/reference/webui.md`.

Recommendation: document first (small doc block in webui.md listing
per-endpoint response shape), migrate to `items` in 0.8.x with a
transition period keeping the old key alongside.
